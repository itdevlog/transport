# Избранное по пользователю (анонимный cookie-профиль) — дизайн

**Дата:** 2026-10-16
**Статус:** одобрен (дизайн), ожидает ревью спеки

## 1. Цель

Дать каждому пользователю личное избранное (маршруты, остановки, заметки, подписи
направлений) без логина и регистрации. Сейчас избранное хранится в одном общем
`favorites.json` — если ссылку на сервис отдать другим, все увидят и будут менять
один общий список. Нужно разделить профили, оставаясь максимально простыми.

## 2. Границы (YAGNI)

- **Никаких** логинов, паролей, аккаунтов.
- **Нет** переноса/восстановления профиля: личность = cookie, срок жизни 1 год.
- **Нет** шаринга избранного и публичных ссылок-профилей.
- **Нет** ограничения числа профилей / очистки «мёртвых» uid (объём копеечный).
- Формы ответов существующих эндпоинтов **не меняются**; фронтенд править не нужно
  (cookie уходит автоматически, запросы same-origin).

## 3. Принятые решения (со слов заказчика)

- Текущее общее избранное → **«перенести на меня»**: существующий список
  привязывается к cookie-профилю браузера заказчика; остальные начинают с пустого.
- Перенос профиля между устройствами — **не делаем** (только cookie, 1 год).
- Хранение — **вариант B: SQLite `profiles.db`, строка на пользователя**.

## 4. Компоненты

### 4.1 `profiles.py` (новый модуль)

Класс `ProfilesStore(db_path)` над SQLite, в стиле `catalog.py` (WAL, короткое
соединение на операцию, `sqlite3.Row`).

Схема:
```sql
CREATE TABLE IF NOT EXISTS profiles (
  uid     TEXT PRIMARY KEY,
  data    TEXT NOT NULL,          -- JSON профиля
  updated INTEGER NOT NULL         -- unix ts
);
```

Методы:
- `get(uid) -> dict` — профиль `{"routes": [...], "stops": [...]}`. Нет строки,
  битый uid или невалидный JSON → возвращает пустой профиль (не бросает наружу).
- `save(uid, data) -> None` — upsert одной строки
  (`INSERT ... ON CONFLICT(uid) DO UPDATE SET data=excluded.data, updated=excluded.updated`).
- Ошибки `sqlite3.Error` обрабатываются вызывающей стороной (фолбэк), конструктор
  и чтения не должны ронять сервер.

Профиль по форме идентичен текущему содержимому `favorites.json`:
```json
{"routes": [{"id": 1554, "number": "87", "name": "..."}],
 "stops":  [{"id": 5830, "name": "Академия тенниса",
            "note": "в школу",
            "dirs": {"Академика Ландау": "домой"}}]}
```

### 4.2 `server.py`

- `FavoritesStore` **сохраняется**, но используется только для чтения старого
  `favorites.json` в момент миграции. Рабочие `/api/favorites` идут через
  `ProfilesStore` + uid.
- Идентичность: на каждом запросе к `/api/*` читаем cookie `marshrut_uid`; если
  нет или значение не проходит валидацию формата (`^[0-9a-f]{32}$`) — генерируем
  `uuid4().hex` и ставим `Set-Cookie`.
- `handle_api(...)` получает профиль по uid и мутирует его теми же действиями
  (`add | remove | note | dir`), что и раньше.

### 4.3 Конфиг и инфраструктура

- `DEFAULTS["profiles"] = {"path": "profiles.db"}`; `config.json` — тот же блок.
- `.gitignore` += `profiles.db`, `favorites.json.migrated`.
- DEPLOY.md: `ReadWritePaths=/opt/transport` уже покрывает `profiles.db`.

## 5. Идентичность (cookie)

- Имя: `marshrut_uid`. Значение: `uuid4().hex` (32 hex-символа).
- Атрибуты: `HttpOnly; SameSite=Lax; Path=/; Max-Age=31536000`
  (+ `Secure`, если соединение по https).
- Выдаётся на первом запросе к `/api/*`, если cookie отсутствует или невалидна.
- Все операции с избранным ключуются по uid.

## 6. Эндпоинты

| Метод | Путь | Поведение |
|---|---|---|
| GET | `/api/favorites` | профиль пользователя (или пустой) |
| POST | `/api/favorites` | `{action, kind, id, name?, note?, where?, label?}` → изменённый профиль |

Ответы и коды ошибок — как сейчас (400 на плохие параметры, 500 на внутренние).
Добавляется только заголовок `Set-Cookie` при выдаче uid.

## 7. Миграция общего избранного

1. При старте, если существует `favorites.json`, помечаем его как «легаси ожидает».
2. Первый браузер, обратившийся к `/api/favorites` и получивший **пустой** профиль,
   «усыновляет» легаси-данные: они записываются как профиль этого uid.
3. Файл переименовывается в `favorites.json.migrated` (повторно не читается).
4. Битый/неправильной формы легаси-файл → игнорируется, пользователь получает
   пустой профиль; файл всё равно переименовывается, чтобы не мешать.

Обоснование: ссылку пока никому не раздавали, поэтому первый обратившийся — владелец.

## 8. Крайние случаи (Review Focus)

1. **Cookies выключены** → каждый запрос новый uid, избранное «не держится», но
   эндпоинт всегда отвечает 200 (сервер не падает).
2. **Подделанный/мусорный uid** в cookie (не `^[0-9a-f]{32}$`) → выдаём новый.
3. **Битый профиль** в БД (не-JSON или не объект) → отдаём пустой профиль.
4. **Повреждённый/недоступный `profiles.db`** → сервер стартует; `/api/favorites`
   отдаёт пустой профиль (фолбэк), не 500.
5. **Конкурентные запросы одного uid** → upsert атомарен (SQLite).
6. **Битый легаси-`favorites.json`** → пропускаем, стартуем с пустого профиля.
7. **Существующие эндпоинты и их формы** не ломаются; старые тесты остаются зелёными
   после адаптации хелпера.

## 9. Тестирование

- `ProfilesStoreTest`: нет профиля → пустой; save/upsert; изоляция двух uid.
- `FavoritesCookieTest`: первый запрос → `Set-Cookie marshrut_uid`; повторный → тот
  же uid; два uid изолированы; мусорный uid заменяется; атрибуты cookie.
- `MigrationTest`: легаси усыновляется один раз + переименование; битый легаси
  игнорируется; второй uid не получает легаси.
- Адаптация существующих `/api/favorites`-тестов на профили (общий хелпер с uid).

## 10. Что НЕ входит

- Аутентификация, аккаунты, восстановление профиля.
- Публичные/шаримые ссылки на избранное.
- Серверная очистка «мёртвых» профилей.
- Изменения фронтенда (кроме, при необходимости, ничего).
